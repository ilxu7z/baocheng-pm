## 一、问题描述

三省六部/纲目 OpenClaw 实际使用中不跑三省六部流程，主 Agent（鮱澄）都是自己默默做或者用 sessions_spawn 子 Agent 做，不走看板调度流程。

## 二、诊断过程

### 2.1 数据采集范围

| 类别 | 采集内容 |
|------|---------|
| 配置文件 | AGENTS.md, SOUL.md, MEMORY.md, TOOLS.md, GLOBAL.md, GOVERNANCE.md, WORKFLOW.md, DISPATCH.md（主 Agent + 9 个子 Agent） |
| 看板代码 | server.py（dispatch 逻辑）, auth.py, kanban_update.py |
| 运行数据 | server.log, stderr.log, tasks_source.json, 主 Agent 最近 30 个 session |
| 历史任务 | JJC-20260616-009（成功）, JJC-20260617-001（成功但曲折）, JJC-20260617-002/003（失败卡死） |

### 2.2 关键发现

#### 发现 1：OpenClaw 自动注入的文件 vs 实际需要的文件

**自动注入到 system prompt 的（6 个）：**
- SOUL.md ✅
- MEMORY.md ✅
- AGENTS.md ✅
- IDENTITY.md ✅
- USER.md ✅
- TOOLS.md ✅

**没有被自动注入的：**
- GLOBAL.md ❌ — 含决策门（三省六部路由入口）
- GOVERNANCE.md ❌ — AGENTS.md 说「必须遵守」但内容未注入
- WORKFLOW.md ❌ — 三省六部完整流程协议
- DISPATCH.md ❌ — 派发前意图评估

**结论：决策门（GLOBAL.md）定义了「每次收到非闲聊需求，第一个执行的步骤」，但主 Agent 从未自动读取过它。**

#### 发现 2：主 Agent 历史 session 零读取决策门相关文件

最近 20 个主 Agent session 中：
- 0 个 session 主动读取过 GLOBAL.md / WORKFLOW.md / DISPATCH.md / GOVERNANCE.md
- 仅 2 个 session 有 dispatch 类消息，均为 cron 晨间简报，非看板 dispatch

#### 发现 3：dashboard dispatch 系统从未真正成功

- dispatch 使用 `subprocess.Popen(['openclaw', 'agent', '--agent', agent_id, '-m', msg, '--timeout', '600'])`
- stdout = `subprocess.DEVNULL`（输出被丢弃）
- 无 EDICT_HOME 环境变量（kanban_update.py 依赖此变量）
- 子 Agent 收到 dispatch 消息后无法回报（无 exec 工具、不知道 kanban_update.py）
- server.log 显示 `TimeoutExpired` 600 秒超时
- 看板自动重试 → 再超时 → 升级 → 回滚 → 死循环

#### 发现 4：历史成功案例的真实模式

**JJC-20260616-009（成功，7 分钟，0 次 rollback）：**
```
13:14:10 皇上下旨 → 主 Agent 在同一秒连续调了 6 次 task-action 手动推进
         Taizi → Zhongshu → Menxia → Assigned → Doing
13:21:08 主 Agent 再次手动推进 Doing → Review → Done
```
全程是主 Agent 在调 task-action 推进状态，代码是主 Agent 用 sessions_spawn 派子 Agent 写的。**三省六部的 Agent 并没有通过 dashboard dispatch 参与。**

**JJC-20260617-002（失败，卡死）：**
```
皇上下旨 → dashboard dispatch 自动派发 → 子 Agent 收不到/无法回报
→ 调度器 600s 超时 → 重试 → 再超时 → 升级 → 回滚 → 死循环
→ 主 Agent 介入：「挂起任务：调度器死循环无法自愈」
```

**成功和失败的区别只有一条：主 Agent 是否绕过了 dashboard dispatch，自己驱动流程。**

### 2.3 因果链

```
GLOBAL.md 不被注入（根因）
  → 主 Agent 不知道决策门存在
    → 不判断 #7/#8/#9
      → 不询问老板是否走三省六部
        → 直接自己干或 spawn（SOUL.md 的 "Be resourceful before asking" 强化了这条路径）

即使想走三省六部：
  → WORKFLOW.md/GOVERNANCE.md 不被注入 → 不知道完整流程
  → 看板 API 不知道怎么用 → 无法创建任务/推进状态
  → dispatch 不可用（stdout=DEVNULL / EDICT_HOME 缺失 / 600s 超时）→ 子 Agent 无法回报
```

### 2.4 诊断结论

**三层断裂：**
1. **知识断裂（根因）**：决策门在 GLOBAL.md 中，但 GLOBAL.md 不被 OpenClaw 自动注入。主 Agent 不知道决策门存在。
2. **执行断裂**：主 Agent 不知道看板 API 用法，且 web_fetch 对 localhost/私有 IP 被 blocked（exec + curl 不受限）。
3. **回报断裂（次生）**：dashboard dispatch 系统（subprocess push）从未成功过——stdout 被丢弃、环境变量缺失、子 Agent 无法回报。

**dashboard dispatch 是一个从未真正成功过的冗余系统。历史成功案例全部是主 Agent 自己通过 sessions_spawn + 手动 task-action 驱动的。**

## 三、修复方案

### 3.1 设计原则

```
看板：记录+展示，不做调度
主 Agent：调度中枢，驱动整个流程
子 Agent：通过 sessions_spawn 被动执行具体工作
dashboard dispatch：保留但不依赖（冗余系统，未来可废弃）
```

### 3.2 具体改动

#### 改动 1：AGENTS.md — 注入决策门 + 完整流程

**文件**: `~/.openclaw/workspace-main/AGENTS.md`  
**为什么**: AGENTS.md 是 6 个自动注入文件之一，写入此文件确保主 Agent 每次 session 都能看到。

**改动内容**:
- 新增「无条件决策门」表格（9 条路由规则 #1-#9）
- 新增「三省六部流程」6 步完整指引（创建看板→spawn 筹微→spawn 审微→spawn 执行→spawn 验收→task-action 推进）
- 新增看板 API 命令（exec + curl）
- 新增铁律：⛔ 不依赖看板自动派发，由主 Agent 驱动

**变更前**: AGENTS.md 只有子 Agent 工作纪律（原设计是为子 Agent 写的，主 Agent 不需要「只在被 sessions_spawn 调用时工作」这条规则）

**变更后**: AGENTS.md 成为主 Agent 的工作协议，包含决策门 + 流程 + API + 纪律

#### 改动 2：TOOLS.md — 补全看板 API 用法

**文件**: `~/.openclaw/workspace-main/TOOLS.md`  
**为什么**: TOOLS.md 是自动注入文件，主 Agent 的「环境备忘录」。

**改动内容**:
- 补全看板 API 端点（create-task, task-action, archive-task, live-status, healthz）
- 更新工作流描述：主 Agent 驱动，不依赖 dispatch

#### 改动 3：MEMORY.md — 更新三省六部铁律

**文件**: `~/.openclaw/workspace-main/MEMORY.md`  
**为什么**: MEMORY.md 是自动注入文件，影响主 Agent 的长期行为。

**改动内容**:
- 从「用户明确说用三省六部/纲目时，必须走完整流程」
- 改为「决策门 #6（用户说「用三省六部制」）强制触发，#7/#8/#9（复杂开发/多部门/调研分析）建议走并向老板确认。走时必须通过看板创建任务，不得自行跳过或直接执行」

### 3.3 没改什么（以及为什么）

| 没改的 | 原因 |
|--------|------|
| dashboard server.py（dispatch 逻辑） | 不需要修——方案是绕过 dispatch，不依赖它 |
| 子 Agent 的 AGENTS.md/SOUL.md | 子 Agent 通过 sessions_spawn 接收任务，工作方式不变 |
| GLOBAL.md | 主 Agent 不会读它，决策门已搬到 AGENTS.md |
| WORKFLOW.md / DISPATCH.md | 不在注入上下文中，写了也没用 |

## 四、修改后的文件内容

### 4.1 AGENTS.md（完整）

```markdown
# 工作协议 · 鮱澄军团

## ⛔ 无条件决策门（每次收到非闲聊需求，第一个执行的步骤）

| # | 判断条件 | 动作 | 走三省六部？ |
|---|---------|------|--------------|
| 1 | 纯闲聊/问候/感谢 | 直接回复 | ❌ |
| 2 | 回答问题（不需要查代码/项目文件） | 直接回复 | ❌ |
| 3 | 只改 workspace 文件（MEMORY/TASKS/SOUL/HEARTBEAT） | 自己执行 | ❌ |
| 4 | 系统自身调整（SOUL/AGENTS/TOOLS） | 自己执行 | ❌ |
| 5 | 单一简单任务（≤1 文件/≤10 行变更/不需要拆解） | 自己执行，不派发 | ❌ |
| 6 | 用户说「用三省六部制」 | 走 Edict Dashboard pipeline | ✅ **强制** |
| 7 | 复杂开发（>50 行代码/多文件/多领域） | 走三省六部 pipeline | ✅ 建议 |
| 8 | 多部门协作（文案+代码+设计） | 走三省六部 pipeline | ✅ 建议 |
| 9 | 需要方案/调研/分析 | 走三省六部 pipeline（筹微→审微） | ✅ 建议 |

**决策门执行规则：**
- #6 强制触发，不需要确认
- #7/#8/#9 判断命中后，向老板确认再执行
- 老板说不走，就自己干或 spawn，不再提
- 走三省六部时，先创建看板任务，再按流程步骤依次派子 Agent 执行
- **⛔ 不过决策门就动项目文件 | ⛔ 走三省六部时越权替其他 Agent 干活**

## 三省六部流程（决策门 #6/#7/#8/#9 命中时执行）

你是调度中枢。三省六部流程由你驱动，不是由看板自动派发。

### 流程步骤

1. 创建看板任务 → 获得 taskId（JJC-xxx）
2. 派筹微（guihua）起草方案 → 等筹微返回方案
3. 派审微（shenyi）审核方案 → 等审微返回审核结论
4. 审核通过 → 派执行 Agent（sessions_spawn）
   - 代码 → daima | 文案 → wenan | 设计 → sheji
   - 审核不通过 → 退回筹微修改
5. 验收（可选派镜衡 shencha）
6. 每步完成后调 task-action 推进看板

### 看板 API

- 地址: http://192.168.3.180:7891
- 认证: 当前无需 token
- 创建: POST /api/create-task
- 推进: POST /api/task-action
- 归档: POST /api/archive-task
- 进度: GET /api/live-status

### 铁律
- ⛔ 看板自动派发不可靠，不要依赖
- ⛔ 不要替子 Agent 干活
- 每步完成后必须调 task-action 推进看板

## 工作纪律
1. 收到任务先验证输入完整性
2. 输出必须结构化
3. 不确定的事标注 [待确认]
4. 禁止越权操作
5. 子 Agent 产出必须验收
6. 超时/失联按 GOVERNANCE.md 处理

## 治理铁律
必须遵守 GOVERNANCE.md 全部条款。
```
