## 审议流程

### 第一步：统一审查（9 维结构化检查 — ✨ vSPEC-KIT 合并版）

逐项审查 TASK.md 的质量，不得跳过。每项标注 ✅ 通过 / ⚠️ 建议 / 🔴 不通过。

```
□ CHK-01 功能完整性 — 所有核心功能点是否有 User Story 覆盖？无遗漏？
□ CHK-02 清晰度 — 每项需求描述无歧义？无「优化」「完善」「适当」等模糊词？
□ CHK-03 一致性 — User Stories 间无矛盾？术语统一？
□ CHK-04 可度量性 — 验收标准可量化可验证（Given-When-Then 或量化指标）？
□ CHK-05 覆盖 — FR-xxx 都有 T-xxx 对应？每个 US 都有子任务？
□ CHK-06 边界/错误 — 异常场景、错误处理已覆盖？Edge Cases 节已填写？
□ CHK-07 非功能性需求 — 性能/安全/可访问性已考虑？约束条件明确？
□ CHK-08 文件冲突 — 冲突矩阵完整？串并行顺序正确（先创建后修改）？
□ CHK-09 占位符 — 是否有未替换的模板占位符？残留 [FEATURE_NAME] / [一句话] 等？
```

**判定规则**：
- 全部 ✅ → 进入第二步
- 有 🔴 → 直接封驳，标注具体项
- 仅 ⚠️ → 条件准奏，附建议

### 第二步：可行性 + 风险 + 协议合规（保留原有核心）

> 统一审查通过后，对方案的可执行性做二次验证。

- [ ] 预估工时是否合理（参考历史数据）？
- [ ] 依赖关系是否形成循环？
- [ ] 关键路径是否可以接受？
- [ ] 高风险项是否有缓解措施？
- [ ] 是否有未确认的假设？
- [ ] Token 预算是否合理？
- [ ] 所有 Agent 职责范围是否正确分配？
- [ ] 需求追溯映射（FR-xxx → T-xxx）是否完整？

### 第三步：多模型交叉评审（硬性要求）

独立审查通过后，**必须**用至少 2 个不同模型对方案进行独立评审。

```
审微独立审查通过
  ↓
模型 A（如 deepseek-v4-pro）→ 独立输出评审意见
模型 B（如 glm-5-turbo）→ 独立输出评审意见
  ↓
合议：比较两个模型的意见
  ↓
有分歧 → 审微做仲裁判断，说明采纳哪方及原因
无分歧 → 综合意见形成最终结论
  ↓
准奏 / 条件准奏 / 封驳
```

**评审维度**（每个模型都必须覆盖）：
- 遗漏风险：是否有子任务/依赖/约束未被覆盖？
- 工时合理性：估算是否过高或过低？
- 文件冲突：是否有审微遗漏的文件共享风险？
- 验收标准：是否每条都可量化、可验证？

**硬性禁止**：
- ❌ 跳过多模型评审直接准奏（违规 = 封驳无效，上报鮱澄）
- ❌ 用同一个模型评审两次当多模型
- ❌ 不记录各模型独立意见，只写综合结论

### 第四步：审议结论
```
✅ 准奏 — 全项通过
⚠️ 条件准奏 — 有建议项但不阻塞执行
🔴 封驳 — 必须修正后重新提交审议
```

封驳时必须附：
- 具体哪一条（CHK-xx 或可行性/风险项）、哪个子任务不通过
- 不通过的原因分类（信息缺失/标准模糊/逻辑矛盾/风险遗漏/占位符未替换）
- 期望的修正方向

## 封驳原则
- 同一个问题封驳 ≤ 2 次
- 第 3 次仍不通过 → 上报鲍澄，附审议记录
- 不是让你挑刺，是让你保底
