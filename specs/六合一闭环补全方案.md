## 〇、概念定义（v2 修正，最终版）

| | SDD（规范驱动） | CDD（协作/上下文驱动） |
|---|---|---|
| **本质** | 一份产出文档：任务「做什么、验收标准、边界」 | 多 Agent 协作约束 + 派发上下文注入 |
| **谁写** | **军师（guihua）写** | **军师写框架 + 系统派发时注入** |
| **防什么** | 防"跑偏做什么" | 防"多 Agent 各干各的、无法对齐" |
| **载体** | `task['spec']`（SDD 契约 dict） | `task['cdd']`（协作契约）+ `_build_knowledge_context` 注入 |

**CDD 定义（按老板）**：管好多 Agent 怎么沟通、信息统一（多任务协作约束）。
- **CDD 框架**（军师写，存 `task['cdd']`）：本任务涉及几个 Agent、各自接口/字段/交接物、对齐规则
- **CDD 注入**（系统做）：派发时把同一套协作约束喂给每个相关 Agent

## 二、SDD 契约 schema（军师产出，存 task['spec']）

```json
{
  "purpose": "一句话目标（为什么做）",
  "outputs": ["交付物1", "交付物2"],
  "acceptance_criteria": ["可验证的 pass/fail 标准1", "...", "标准N"],
  "boundaries": ["不做什么", "范围边界"],
  "dependencies": ["前置依赖", "外部系统"],
  "edge_cases": ["异常场景", "边界条件"],
  "fuzzy_free": true
}
```

**军师（guihua）强制要求**（写入 `agents/guihua/AGENTS.md`）：
> 起草任何执行方案前，必须产出 SDD 契约（spec），含全部字段；acceptance_criteria 必须可验证（pass/fail），不得含模糊词（尽快/适当/合理/必要时/优化/提升等）。

## 三、CDD 协作契约 schema（军师产出框架，存 task['cdd']）

```json
{
  "agents": [
    {"agent": "daima", "role": "开发部", "deliverables": ["接口实现"]},
    {"agent": "sheji", "role": "设计部", "deliverables": ["UI 标注"]},
    {"agent": "wenan", "role": "内容部", "deliverables": ["文案"]}
  ],
  "interfaces": [
    {"from": "daima", "to": "sheji", "contract": "接口字段: {id, name, price}", "must_match": "约定字段名统一"},
    {"from": "sheji", "to": "wenan", "contract": "文案长度 ≤30 字"}
  ],
  "alignment_rules": [
    "所有 Agent 使用同一套验收标准（spec.acceptance_criteria）",
    "接口字段命名统一，任何人不得私自改名",
    "交接物必须写到 shared-knowledge 供下游读取"
  ]
}
```

**系统注入**（server.py 扩展 `_build_knowledge_context` 或新增 `_build_cdd_context`）：
- 派发时把 `task['cdd'].interfaces + alignment_rules` 注入给**每个涉及 Agent**
- 保证多 Agent 干同一任务时，看到的是同一套协作约束（信息统一）

## 四、闭环流程（最终版）

```
老板下需求（创建任务）
  │
  ▼
① 军师写 SDD(规范) + CDD(协作框架)  → 提交 /api/spec-submit
  │
  ▼
② 七维自检评分(selfcheck D1-D7) → 短板清单(short_dims)
  │
  ▼
③ ↻ 迭代补齐循环（iterate_engine.py）
  │   按短板生成补齐动作 → 提示军师补齐 → 重评
  │   直到「落地把握度 ≥98% 且无短板」才放行   ← 老板要求的流程
  │
  ▼
④ 老板确认闸（awaiting_boss）
  │  /api/boss-confirm: 通过→继续 / 驳回+意见→退回规划部
  │  豁免: 任务 manual_spec=skip（老板明确"方案已定只落地"）→跳过
  │
  ▼
⑤ 执行办派发 + 六部自动执行
  │  Assigned→Doing 读 task.targetDept 写回 org → 自动派发对应六部
  │  同时注入 CDD 协作约束给各方
  │
  ▼
⑥ 品控验收（/api/qa-result）PASS→ Done / FAIL→ 自动打回列出部门
  │  OCR 评审层在 Review 时已自动跑（已有）
  │
  ▼
⑦ Done → SE 经验卡回流（已有）→ lossless-claw 记录（已有）
```

## 六、灰度与风险

1. **先灰度**：SIX_UNITY=1 + ITERATE_ENFORCE=1 仅对 1-2 个开发测试任务开，验证全链路
2. **兼容旧任务**：无 spec 的存量任务不强制补，只对新任务生效
3. **老板确认不阻塞紧急**：manual_spec=skip 高优通道
4. **六合一门禁原开关保留**：SIX_UNITY 默认仍 0（安全），灰度验证后由老板决定全开

## 七、验收标准

- [ ] 新建任务 → 军师提交 SDD+CDD（非 None，契约完整）
- [ ] spec 初评 <98% → 自动产短板 → 军师补齐 → 重评至 ≥98% 才放行
- [ ] ≥98% → awaiting_boss，未确认无法 advance
- [ ] 老板驳回→退回规划部；通过→执行；豁免→跳过
- [ ] 执行办选 targetDept → 自动派发六部，CDD 注入各方
- [ ] 品控 FAIL→自动打回；PASS→Done；OCR 评审层照常
- [ ] 全程可观测（flow_log + spec_status + cdd + iterate + audit）
- [ ] **本地 git 最新（commit+push）+ GitHub 同步最新**
