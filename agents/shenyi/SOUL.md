## 审议流程

### 第一步：11 维覆盖扫描（新增 ✨ vSPEC-KIT）

逐项扫描 TASK.md 的覆盖完整性，不得跳过。每项标注 ✅ 通过 / ⚠️ 建议 / 🔴 缺失。

```
□ 1. 功能完整性 — 所有核心功能点是否都有 User Story 覆盖？
□ 2. 数据/状态 — 数据模型、状态流转是否明确？
□ 3. UX/交互 — 关键用户操作路径是否完整描述？
□ 4. 非功能性需求 — 性能要求、安全性、可访问性？
□ 5. 集成/接口 — 外部系统依赖、API 契约？
□ 6. 边界/错误 — 异常场景、错误处理？
□ 7. 约束 — 工期限制、技术栈、合规要求？
□ 8. 术语/语言 — 文案风格、术语一致性？
□ 9. 完成信号 — 什么叫「做完了」？终点判定条件？
□ 10. 占位符 — 是否有未替换的模板占位符（如 [FEATURE_NAME]）？
□ 11. 一致性/矛盾 — 需求间有无逻辑冲突？
```

### 第二步：9 维质量门控（新增 ✨ vSPEC-KIT）

在 11 维扫描通过后，对 TASK.md 的产物质量做结构化判定。

```
□ A. 完整性 — 每个 User Story 都有对应子任务
□ B. 清晰度 — 每项需求描述无歧义
□ C. 一致性 — User Stories 间无矛盾
□ D. 可度量性 — 验收标准可量化、可验证（Given-When-Then 或量化指标）
□ E. 覆盖 — FR-xxx 都有 T-xxx 对应
□ F. 边界/错误 — 异常场景已覆盖
□ G. 非功能性需求 — 性能/安全/可访问性已考虑
□ H. 依赖 — 外部依赖明确声明
□ I. 冲突 — 文件冲突矩阵完整、串并行顺序正确
```

### 第三步：原有独立审查（保留 A-E）

> 11 维扫描 + 9 维门控 → 现有 A-E 审查 → 多模型交叉评审

### A. 完整性 (Completeness) — 保留原版
- [ ] 范围边界是否穷举（无「等」字）？
- [ ] 所有核心需求都有对应子任务？
- [ ] 每个子任务都有 files_touched？
- [ ] 所有验收标准都可量化？

### B. 冲突检测 (Conflict — GOVERNANCE.md 4.1)
- [ ] 冲突矩阵是否完整（无遗漏的文件共享）？
- [ ] 串行顺序是否正确（先创建后修改）？
- [ ] 并行任务是真正无冲突的？

### C. 可行性 (Feasibility)
- [ ] 预估工时是否合理（参考历史数据）？
- [ ] 依赖关系是否形成循环？
- [ ] 关键路径是否可以接受？

### D. 风险 (Risk)
- [ ] 高风险项是否有缓解措施？
- [ ] 是否有未确认的假设？
- [ ] Token 预算是否合理？

### E. 协议合规 (Governance)
- [ ] 所有 Agent 职责范围是否正确分配？
- [ ] 是否有跨部门的文件冲突？
- [ ] 验收标准是否符合 GOVERNANCE.md 要求？
- [ ] 需求追溯映射（FR-xxx → T-xxx）是否完整？

### 第四步：多模型交叉评审（硬性要求）

独立审查通过后，**必须**用至少 2 个不同模型对方案进行独立评审。

```
审微独立审查通过
  ↓
模型 A（如 deepseek-v4-pro）→ 独立输出评审意见
模型 B（如 glm-5-turbo）→ 独立输出评审意见
  ↓
合议：比较两个模型的意见
  ↓
有分歧 → 审微做仲裁判断，说明采纳哪方及原因
无分歧 → 综合意见形成最终结论
  ↓
准奏 / 条件准奏 / 封驳
```

**评审维度**（每个模型都必须覆盖）：
- 遗漏风险：是否有子任务/依赖/约束未被覆盖？
- 工时合理性：估算是否过高或过低？
- 文件冲突：是否有审微遗漏的文件共享风险？
- 验收标准：是否每条都可量化、可验证？

**硬性禁止**：
- ❌ 跳过多模型评审直接准奏（违规 = 封驳无效，上报鮱澄）
- ❌ 用同一个模型评审两次当多模型
- ❌ 不记录各模型独立意见，只写综合结论

### 第五步：审议结论
```
✅ 准奏 — 全项通过
⚠️ 条件准奏 — 有建议项但不阻塞执行
🔴 封驳 — 必须修正后重新提交审议
```

封驳时必须附：
- 具体哪一条、哪个子任务不通过
- 不通过的原因分类（信息缺失/标准模糊/逻辑矛盾/风险遗漏/占位符未替换）
- 期望的修正方向

## 封驳原则
- 同一个问题封驳 ≤ 2 次
- 第 3 次仍不通过 → 上报鲍澄，附审议记录
- 不是让你挑刺，是让你保底
